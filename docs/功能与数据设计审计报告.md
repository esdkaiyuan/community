## 一、空转功能（前端有入口、后端不产数据）—— 最高优先级

### 1.1 「编辑推荐 / 热门」筛选永远返回空列表 🔴

**证据（线上库实测）**

```
is_hot=1 项目数:       0
is_recommend=1 项目数: 0
项目总数:              18
```

**链路**：前端 `HomeView.vue` 的 FILTERS 发 `filter=recommend|hot`
→ 控制器 `...req.query` 透传
→ `project.service.js:170-171`：`if (filter==='recommend') where.is_recommend = 1` / `if (filter==='hot') where.is_hot = 1`

**病灶**：全仓**没有任何代码写入** `is_recommend` / `is_hot`（grep 结果只有读取与排序，无写入）。这两个标记只能人工改库，线上永远是 0 → 用户点「编辑推荐」「热门」必得空列表。

> 注意区分：`sort=hot` 是按 `like_count DESC` 排序（这个正常，不依赖标记位）；坏的只有 `filter=hot` / `filter=recommend`。

**修法（二选一）**
- A. 给标记位定计算口径：近 7 天 trend score 超阈值自动置 `is_hot=1`（定时任务或查询时计算并落库），`is_recommend` 走运营后台人工打标 + 管理接口
- B. 取消 filter 语义，把这两个入口直接映射为排序（与 `sort=hot` 合并），删除 `is_hot`/`is_recommend` 字段

### 1.2 `projects.status` 是死字段 🔴

`schema.sql` 声明 `status TINYINT DEFAULT 0 COMMENT '0-正常'`，但全仓零使用（grep 到的 status 全是 `project_comments.status`，不是项目的）。前端也没有项目状态（招募中/进行中/已完成）与草稿箱。

**修法**：要么删除该字段，要么启用为状态机（0 草稿 / 1 招募中 / 2 进行中 / 3 已完成），列表默认只出已发布。

## 三、数据设计缺陷

### 3.1 schema 漂移：声明 14 张表，线上只有 12 张 🔴

**线上实测表清单（information_schema）**

```
activity_logs, categories, comment_likes, notifications, project_comments,
project_favorites, project_likes, project_participants, project_views,
projects, security_events, users
```

`schema.sql` 里声明、线上**从未创建**的两张表：`tags`、`project_tags`。
对应的 `Tag` / `ProjectTag` 两个模型也从未被任何 service/controller 引用（但 `models/index.js` 仍注册了关联）。

**真实标签存储**：`projects.tags` JSON 列（TEXT），`JSON_CONTAINS` 精确匹配。

**后果**
1. 新环境按 `schema.sql` 建库会多出两张永不使用且与真实数据不一致的死表
2. 想做「标签页 / 标签去重 / 标签改名 / 标签维度统计」时无表可用
3. schema 与实际长期漂移，是后期最难查的一类债

**修法（二选一，必须落到 schema.sql）**
- A. 承认 JSON 列方案：从 `schema.sql` 删除 `tags`/`project_tags` 建表语句，删除 `Tag`/`ProjectTag` 模型与 `models/index.js` 关联
- B. 启用关系表：补建两表 + 写迁移脚本把 `projects.tags` 回填到关系表 + 读写切到关系表（工作量明显更大，但换来标签可治理）

### 3.2 热门标签全表扫 + 内存聚合 🟡

`listPopularTags`：`SELECT tags FROM projects WHERE tags IS NOT NULL` 把全表捞进 Node，用 Map 逐条聚合。
数据量一大就是全表扫描 + 大内存 + 无缓存，且无法分页。

**修法**：启用 `project_tags` 后 `GROUP BY tag_id` 聚合；或加定时物化/缓存（标签变化频率低，性价比高）。

### 3.3 计数器读改写竞态 🔴

```js
// project.service.js likeProject
await ProjectLike.create({ project_id: id, user_id: userId })
project.like_count += 1
await project.save()          // ← 读改写，无事务、无原子增量
```

同样模式出现在：取消赞、参与/取消参与、评论计数（`comment.service.js:208/273/293/316`）。
并发下会丢更新（两个请求同时读到 5，都写 6）。

唯一正确的写法在 `comment.service.js:331`：删除后 `Project.update({ comment_count: count })` 重算——**口径不统一**本身就说明这块是补丁堆出来的。

**修法**：统一改为原子增量
```js
await Project.increment('like_count', { where: { id } })            // 增
await sequelize.query('UPDATE projects SET like_count = GREATEST(like_count - 1, 0) WHERE id = ?', ...)  // 减
```

### 3.4 高频排序无索引 🟡

`projects` 现有索引只有：`idx_creator(creator_id)`、`idx_category(category_id)`、`idx_deleted_at(deleted_at)`。

未覆盖的高频路径：
- `ORDER BY created_at DESC`（默认 sort=latest，最高频入口）→ filesort
- `ORDER BY like_count DESC`（sort=hot）→ filesort
- `ORDER BY participant_count DESC`（sort=participants）→ filesort
- 标签筛选 `JSON_CONTAINS(tags, ...)` → 无函数索引/生成列，永远全表

**修法**：补 `idx_created_at`、`idx_like_count`、`idx_participant_count`；标签若启用关系表则走 `project_tags(tag_id, project_id)` 联合索引。

### 3.5 软删除与计数口径（3.3 的伴生问题）

`paranoid: true` 已正确启用（Sequelize 自动过滤 `deleted_at`）✅，但 `project_likes` 等唯一键对已软删项目仍占位；计数自增自减与重算两种口径混用。

## 关键证据

**建库链路实测（修复后）**

```
隔离命名空间下真的建一遍：12/12 张表创建成功，零错误
与线上比对：列（类型+可空）0 处漂移 · 索引 0 处漂移 · 外键 19/19 逐列一致
唯一差异：4 处 updated_at 默认值（已在 schema.sql 头部注明理由 —— 线上用的
          零日期默认值在 MySQL 8 默认 sql_mode 下不可移植）
```

**红证（把缺陷重新注入，确认断言真会变红）**

| 注入的缺陷 | 触发的断言 |
| --- | --- |
| `categories` 索引行尾多逗号 | S12 → `ERROR 1064` |
| 外键引用后声明的表 | S11 + S12 → `ERROR 1824` |
| 漏写 `PRIMARY KEY` | S12 → `ERROR 1075` |
| `users.id` 改回有符号 INT | S14 → 列漂移 + `ERROR 3780` |
| 删掉 `idx_like_count` | S15 → 索引漂移 |
| 删掉 `project_views` 两条外键 | S15 → 外键漂移 |

**为什么此前 12 条断言全绿却漏掉这些**：S1~S10 只做「正则解析 + 比对元数据」，
而这三类错误**只有在真的执行 `CREATE TABLE` 时才暴露**。更隐蔽的是，拿 schema.sql
对线上库跑一遍也没用 —— 全是 `CREATE TABLE IF NOT EXISTS`，表已存在时 MySQL
直接跳过执行、只做解析，`ERROR 1075` 这类语义错误照样漏网。
所以新增的 S12 走的是**隔离命名空间真实建表**（`zzverify_` 前缀，建完即删）。

# 第四轮：全量回归里的「假绿」与上传残留（2026-10-03）

改密功能完成后跑全量回归（37 个脚本），**5 个失败**。逐条查下来，只有 1 个是产品缺陷，
其余分别是「测试自己腐烂」和「本机沙箱守卫」。本轮的价值主要在**验证纪律**上。

## 🔴 真实缺陷：上传被拒不清理临时文件（已修）

**现象**：连续 POST 超 5MB 的图片，接口每次都正确返回 400，但磁盘上**每次多留一个 5MB 文件**。

**根因**（`backend/src/middleware/upload.js`）：multer 的 `diskStorage` 是**先落盘、再判断**。
`limits.fileSize` 触发时，文件已经在磁盘上了，而错误翻译分支只做了「把 MulterError 翻成 400」，
**没有任何删除动作**。对照之下，魔数校验失败那条路径（`assertRealImage`）是有 `unlinkSync` 的 ——
所以「不是图片」不留垃圾，「图片太大」却留，属明确的遗漏。

**风险**：不需要任何权限，一个循环请求就能把磁盘打满。

**修法**：`discard(file)` + `discardInflight(req)`；路径由 `storage.filename` 记到 `req._inflightPath`
（超限时 `req.file` / `err.file` 都还没挂上，只有这里拿得到）。

**踩过的坑（重要）**：第一版用「拍目录快照 → 差集删除」来兜底，**是错的**。
两次上传相邻时，后一个请求的快照早于前一个文件落盘，差集会把**别人的文件**一起删掉 ——
实测 `cover_compress` 直接 8 条红（小图 / GIF 上传成功后文件被误删）。
用 `git show HEAD:` 切回原始版做隔离对照才定位到，确认是本次改动引入的回归。
**要删就记确切路径，绝不靠猜。**

## 🔴 假绿：`verify_mentions.py` 崩了却报 PASS（已修）

**现象**：汇总里 `verify_mentions.py` 是 PASS / `EXIT=0`，但日志里它只打印到 `A1` 就断了。

**两个叠加的原因**：
1. SQL 笔误：`SELECT … FROM notifications WHERE … AND n.user_id = ?` —— `FROM` 上**少了别名 `n`**，
   `n.user_id` 直接报 Unknown column，A2 必崩。
2. 脚本用 `try: main() except BaseException: traceback.print_exc() finally: finish()` 做清场，
   而 `finish()` 只看 `assert_fails` / `console_errors` —— **崩溃两者都不碰**，
   于是退出码 0、汇总 PASS，实际 A2~A8 与整段页面测试全都没跑。

**修法**：`_verify_common.py` 新增 `crash(exc)`，把未捕获异常登记成一次失败；
`verify_mentions.py` 的 `except` 调它。**另有 4 个脚本（counter_atomicity / popular_tags /
project_flags / rich_text）本来就有 `_ERRORED -> sys.exit(1)`，行为是对的，不要照抄改。**

**见证红**：把 `crash()` 掏空 → 崩溃退回 `EXIT=0 / assert failed: 0`（假绿原形毕露）；
还原 → `EXIT=1 / FAIL 脚本中途崩溃`。证明记账机制本身有效，而不是碰巧绿。

**副产物**：`zzverify_crash_probe.py` 这个见证红探针因为命名像正式脚本，被
`run_verify_suite.py` 收集进全量套件跑了一遍 —— 临时注入的副本**必须当轮删掉**。

## ⚠️ 本机沙箱的删除守卫（环境问题，非代码）

**现象**：一轮对话内删除量超过阈值（50）后，**后台任务进程**里所有 `fs.unlinkSync` 抛
`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`；而**前台工具调用发起的进程照常删除成功**
（同一份代码、同一台机，差异只在进程上下文，已用独立探针双向验证）。

**后果**：`cover_upload` / `cover_crop` / `rich_text` 的「回收旧文件 / 被拒不残留」类断言恒红，
而应用对回收失败是**刻意静默吞掉**的，看着像功能坏了。

**处置**（不掩盖、不删断言）：
- `verify_cover_upload.py` 补 `backend_can_delete(token)` 探针 —— 让后端走一次**它自己的**
  unlink（文本改名 `.png` → 魔数不过 → 删文件）。删得掉就跑断言，删不掉就**明确 SKIP 并打印原因**。
  **断言不能删**：CI（GitHub Actions）没有这个守卫，那里必须真跑。
- `except OSError` **抓不住**这个守卫（它抛 `SystemExit`，继承 `BaseException`），
  结果清理动作把整个脚本带崩。已在 3 个封面脚本 + rich_text 共 **7 处**补 `except BaseException`。

## ⚠️ 测试自己腐烂：`verify_home_favorites.py`

断言 `cards.count() == len(all_ids)`（「首页展示全部项目」）。库里项目涨到 18、

（把 12 抄进断言等于「测试与实现各写一份」，常量改了测试照样绿）。
现库内 18 个项目，单跑 `EXIT=0 / 19 OK`。

**通用判据**：断言里出现**会随数据增长变化的数量**时，先问「数据涨到 100 倍它还成立吗」。
