### 修复过程中新发现的问题

1. **存量数据没有任何标签**：18 个活跃项目的 `tags` 全为 NULL，所以热门标签接口
   恒返回空。前端已有 `DEFAULT_TAG_SUGGESTIONS` 兜底（输入侧不空白），标签筛选
   chip 也因无数据而不显示——**没有形成空入口**，但「标签」这条业务线实际是空的。
   是否给存量项目补标签属于运营决策。
2. **线上库沉淀了大量验证脚本的残留项目**（如 #916「评论点赞验证项目」、
   #950-952「移动端分页填充项目」），会混进「精选」结果。清理属于运维操作，
   涉及真实数据，需你确认后再做。
3. **既有测试断言缺陷**：`verify_card_favorite` 拿「库里全部项目数」去比
   「首页渲染的卡片数」（18 vs 12），恒定失败；已改为按页面实际卡片数比对。
4. **索引反向漂移**：线上有 `idx_created` / `idx_status` 等 schema 从未声明的索引，
   属于「文档落后于库」的另一面，已在修复中一并补齐文档。

## 一、空转功能（前端有入口、后端不产数据）—— 最高优先级

### 1.1 「编辑推荐 / 热门」筛选永远返回空列表 🔴

**证据（线上库实测）**

```
is_hot=1 项目数:       0
is_recommend=1 项目数: 0
项目总数:              18
```

**链路**：前端 `HomeView.vue` 的 FILTERS 发 `filter=recommend|hot`
→ 控制器 `...req.query` 透传
→ `project.service.js:170-171`：`if (filter==='recommend') where.is_recommend = 1` / `if (filter==='hot') where.is_hot = 1`

**病灶**：全仓**没有任何代码写入** `is_recommend` / `is_hot`（grep 结果只有读取与排序，无写入）。这两个标记只能人工改库，线上永远是 0 → 用户点「编辑推荐」「热门」必得空列表。

> 注意区分：`sort=hot` 是按 `like_count DESC` 排序（这个正常，不依赖标记位）；坏的只有 `filter=hot` / `filter=recommend`。

**修法（二选一）**
- A. 给标记位定计算口径：近 7 天 trend score 超阈值自动置 `is_hot=1`（定时任务或查询时计算并落库），`is_recommend` 走运营后台人工打标 + 管理接口
- B. 取消 filter 语义，把这两个入口直接映射为排序（与 `sort=hot` 合并），删除 `is_hot`/`is_recommend` 字段

### 1.2 `projects.status` 是死字段 🔴

`schema.sql` 声明 `status TINYINT DEFAULT 0 COMMENT '0-正常'`，但全仓零使用（grep 到的 status 全是 `project_comments.status`，不是项目的）。前端也没有项目状态（招募中/进行中/已完成）与草稿箱。

**修法**：要么删除该字段，要么启用为状态机（0 草稿 / 1 招募中 / 2 进行中 / 3 已完成），列表默认只出已发布。

## 三、数据设计缺陷

### 3.1 schema 漂移：声明 14 张表，线上只有 12 张 🔴

**线上实测表清单（information_schema）**

```
activity_logs, categories, comment_likes, notifications, project_comments,
project_favorites, project_likes, project_participants, project_views,
projects, security_events, users
```

`schema.sql` 里声明、线上**从未创建**的两张表：`tags`、`project_tags`。
对应的 `Tag` / `ProjectTag` 两个模型也从未被任何 service/controller 引用（但 `models/index.js` 仍注册了关联）。

**真实标签存储**：`projects.tags` JSON 列（TEXT），`JSON_CONTAINS` 精确匹配。

**后果**
1. 新环境按 `schema.sql` 建库会多出两张永不使用且与真实数据不一致的死表
2. 想做「标签页 / 标签去重 / 标签改名 / 标签维度统计」时无表可用
3. schema 与实际长期漂移，是后期最难查的一类债

**修法（二选一，必须落到 schema.sql）**
- A. 承认 JSON 列方案：从 `schema.sql` 删除 `tags`/`project_tags` 建表语句，删除 `Tag`/`ProjectTag` 模型与 `models/index.js` 关联
- B. 启用关系表：补建两表 + 写迁移脚本把 `projects.tags` 回填到关系表 + 读写切到关系表（工作量明显更大，但换来标签可治理）

### 3.2 热门标签全表扫 + 内存聚合 🟡

`listPopularTags`：`SELECT tags FROM projects WHERE tags IS NOT NULL` 把全表捞进 Node，用 Map 逐条聚合。
数据量一大就是全表扫描 + 大内存 + 无缓存，且无法分页。

**修法**：启用 `project_tags` 后 `GROUP BY tag_id` 聚合；或加定时物化/缓存（标签变化频率低，性价比高）。

### 3.3 计数器读改写竞态 🔴

```js
// project.service.js likeProject
await ProjectLike.create({ project_id: id, user_id: userId })
project.like_count += 1
await project.save()          // ← 读改写，无事务、无原子增量
```

同样模式出现在：取消赞、参与/取消参与、评论计数（`comment.service.js:208/273/293/316`）。
并发下会丢更新（两个请求同时读到 5，都写 6）。

唯一正确的写法在 `comment.service.js:331`：删除后 `Project.update({ comment_count: count })` 重算——**口径不统一**本身就说明这块是补丁堆出来的。

**修法**：统一改为原子增量
```js
await Project.increment('like_count', { where: { id } })            // 增
await sequelize.query('UPDATE projects SET like_count = GREATEST(like_count - 1, 0) WHERE id = ?', ...)  // 减
```

### 3.4 高频排序无索引 🟡

`projects` 现有索引只有：`idx_creator(creator_id)`、`idx_category(category_id)`、`idx_deleted_at(deleted_at)`。

未覆盖的高频路径：
- `ORDER BY created_at DESC`（默认 sort=latest，最高频入口）→ filesort
- `ORDER BY like_count DESC`（sort=hot）→ filesort
- `ORDER BY participant_count DESC`（sort=participants）→ filesort
- 标签筛选 `JSON_CONTAINS(tags, ...)` → 无函数索引/生成列，永远全表

**修法**：补 `idx_created_at`、`idx_like_count`、`idx_participant_count`；标签若启用关系表则走 `project_tags(tag_id, project_id)` 联合索引。

### 3.5 软删除与计数口径（3.3 的伴生问题）

`paranoid: true` 已正确启用（Sequelize 自动过滤 `deleted_at`）✅，但 `project_likes` 等唯一键对已软删项目仍占位；计数自增自减与重算两种口径混用。

- 富文本 / @ 提及 / 浏览量去重 / 深色模式 / 移动端触控 / CI / 单测 均已落地并有验证脚本
