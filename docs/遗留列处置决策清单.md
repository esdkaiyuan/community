## 为什么会有这些列

它们**不属于当前设计**，是更早版本留下的。`schema.sql` 如实声明它们，是为了守住
「新环境建库结果 == 生产结构」这个不变量（`verify_schema_consistency.py` 的 S14/S15
会逐列比对线上，声明缺失即报漂移）。**声明 ≠ 认可**，删列要同时改线上 + schema。

## 一、事实核验：先纠正旧结论

旧清单写「12 个」，表里只列了 9 个，且把 `projects.end_date` 标成「—」。
逐列实测后的真实情况是 **9 个**：

| # | 表.列 | 线上存在 | 非默认/非空行数 | 全仓引用 |
| --- | --- | --- | --- | --- |
| 1 | `users.is_admin` | ✅ | **1**（1 个管理员） | 仅 schema.sql |
| 2 | `users.status` | ✅ | 0（全为 1） | 仅 schema.sql |
| 3 | `categories.project_count` | ✅ | **8**（全部有值） | 仅 schema.sql |
| 4 | `categories.status` | ✅ | 0（全为 1） | 仅 schema.sql |
| 5 | `projects.status` | ✅ | **33**（35 个中 33 个非 1） | schema.sql + **模型已声明** |
| 6 | `projects.repository_url` | ✅ | **10** | 仅 schema.sql |
| 7 | `projects.end_date` | ✅ | **10**（4 个不同日期） | 仅 schema.sql |
| 8 | `projects.access_type` | ✅ | 0（全为 `public`） | 仅 schema.sql |
| 9 | `projects.access_password` | ✅ | 0（全为 NULL） | 仅 schema.sql |

`users.last_login_at` 线上无此列（不算）。

> 🔎 **核验方法上的一个坑（值得记下）**：我用 `SELECT … WHERE end_date IS NOT NULL`
> 探测时得到「列不存在」，差点把它当成本不存在写进清单。真相是列**确实存在**，
> 探测脚本把 `sql_one()` 的异常吞成了「列不存在」——一个**假阴性**。
> 后来改用 `information_schema` + `LOWER(column_name)` 逐列直查才对上。
> **教训：判断「某列/某表是否存在」必须查 `information_schema`，
> 不要靠一次业务查询的成败来推断** —— 后者会把「查询出错」误报成「对象不存在」。

### 一个容易误判的点：`projects.status` 在模型里声明了

`backend/src/models/Project.js` 确实有 `status: { type: TINYINT, defaultValue: 0 }`，
看起来像「在用」。**但实测接口不返回它** —— service 层用显式字段白名单挑选，
`GET /projects` 返回的字段里没有 `status`：

```
返回字段: categoryId categoryName commentCount coverImage createdAt creator
         description id isHot isRecommend likeCount participantCount tags title viewCount
含 status ? False
```

所以「零读写」结论成立，但准确说法是：**模型声明了、service 不取、前端拿不到**。
这也解释了为什么它一直没被发现——从外面看它像是「半成品功能」，实际是彻底的死字段。
清理时**模型里的声明要一并删**，否则 Sequelize 仍会往 SELECT 里带这一列。

## 二、按数据风险分级

删列是**不可逆**的（`ALTER TABLE DROP COLUMN` 没有回滚，除非事先 dump）。按「删了会丢什么」分三档：

### A 档 · 删了**零数据损失**（4 个，建议直接清理）

| 列 | 理由 |
| --- | --- |
| `users.status` | 40 行全为 1，无任何差异化取值 |
| `categories.status` | 8 行全为 1 |
| `projects.access_type` | 35 行全为 `public` |
| `projects.access_password` | 35 行全为 NULL |

这 4 列既无差异化数据、又无代码引用，属于纯粹的 schema 噪音。留着只会让人
误以为「有状态机/有私密项目」，进而写出错误的代码或文档。

### B 档 · 有数据，但**数据本身无意义**（1 个，建议清理 + 先备份）

| 列 | 情况 | 说明 |
| --- | --- | --- |
| `categories.project_count` | 8 行有值，样本 133 | **与真实值严重不符**（实际项目数远小于此）。代码里分类项目数是**实时 count** 算出来的，这个物化列是旧实现残留，值本身已是脏数据 |

### C 档 · 有数据，**删之前必须先决定保留什么**（4 个）

| 列 | 数据 | 决策点 |
| --- | --- | --- |
| `users.is_admin` | 1 个管理员 | 🔴 **这行数据是真信息**。要么接成真功能（管理员后台），要么先导出留档再删。直接删 = 那个管理员身份凭空消失 |
| `projects.repository_url` | 10 个项目有仓库地址 | 🟡 10 条真实 URL。**建议先接成真功能**（详情页展示仓库链接，成本很低），确认没人用再删列 |
| `projects.end_date` | 10 个项目有截止日期（`2026-05-20` / `2026-06-09` / `2026-06-15` / `2026-09-01`） | 🟡 **这批日期全都已过期**。要么接成「已截止」标记（改动极小、语义立刻成立），要么确认无人用后删 |
| `projects.status` | 33 个非 1 | 🟡 需确认这些取值是否承载真实语义（如「已下架」的项目不该出现在广场）。若是，则应**接成真功能**（下架/完成状态机）而不是删 |

## 三、两个方向（请选一个，或按档位混合）

### 方向 1 · 全部清理（推荐）
- A 档 4 个：直接删。
- B 档 1 个：删（数据本就是脏的），删前 dump 一次 `categories` 表。
- C 档：`is_admin` 先导出留档；`repository_url` / `end_date` **建议改走方向 2 接成真功能**
  （两处各 10 行真实数据，成本都很低、接上就立刻有产品价值）；`projects.status`
  确认语义后删或启用。
- 同步动作：线上 `ALTER TABLE DROP COLUMN` + 从 `schema.sql` 移除 + **从 `Project.js` 移除 status 声明** + 跑 `verify_schema_consistency.py` 确认 S14/S15 无漂移。

### 方向 2 · 部分启用（只启用有真实价值的）
- `repository_url` → 详情页展示「查看仓库」链接（半小时内可完成，10 条数据立刻变现）。
- `end_date` → 已过期的项目在卡片/详情上标「已截止」（4 个日期全是过去时间，语义天然成立）。
- 其余保持遗留不动。**遗留列本身不构成风险**，只要 schema.sql 如实声明、不被误当成功能。

## 四、执行时必须注意的坑

1. **删列前先 dump**：`mysqldump` 相关表，或至少把 C 档三列的取值导成 CSV 留档。`DROP COLUMN` 无法回滚。
2. **模型声明要一起删**：`Project.js` 的 `status` 留着，Sequelize 会继续 SELECT 它——虽然 service 用白名单挡住了，但一旦有人改成 `findAll()` 直接返回，就会把死字段重新暴露出去。
3. **schema.sql 必须同步**：线上删了、schema.sql 不删 → `verify_schema_consistency.py` 的 S14 会报漂移（这是好事，别绕过）。
4. **别把清理当紧急事项**：这些列不影响任何现有功能（接口不返回、前端不读）。真正紧急的是另一件事——
